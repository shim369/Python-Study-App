# review-exercise

演習の品質ゲート。**読むだけで判断せず、怪しい点は実際にコードを採点して確かめる。**

## 入力
- 対象: 演習 id(複数可)、レベル、または「全部」。指定がなければユーザーに確認する

## 手順(1問ごと)
1. **読む**: `exercises/level<N>/<NNN>_<slug>/exercise.yaml` と `test_solution.py` を全部読む
2. **自動検証**: `uv run python scripts/verify_solutions.py --id <id>`
   (模範解答が合格・初期コードが不合格であること)
3. **観点ごとに確認**(下記チェックリスト)
4. **抜け穴の実証**: 怪しいと思ったら「ずるい解答」をスクラッチパッドに書いて採点する
   `uv run python scripts/verify_solutions.py --id <id> --try <ファイル>`
   - 最低限ためすもの: 説明文の例だけを `if` で返す解答 / 仕様の一部を無視した解答
     (例: 空入力の扱いを書かない、順序を保たない、引数を書き換える)
   - **合格してしまったら抜け穴**。テストを追加して、再度 `--try` で不合格になることを確認する
5. **ヒントの検証**: ヒント3の手順どおりに素直に書いた解答が合格するか(仕様との食い違いがないか)。
   疑わしければ実際に書いて `--try` する
6. 修正した場合は `verify_solutions.py --id <id>` と `uv run ruff check exercises` を再実行する

## チェックリスト
### 問題文(description)
- 関数名・引数・戻り値の型と意味が書かれている
- 境界の扱い(空・0・負数・重複・大文字小文字・範囲の端が「以上/未満」のどちらか)が書かれている
- 例が1つ以上あり、例の値がテストと矛盾しない
- テストで確かめている仕様が、すべて問題文に書かれている(**書かれていない仕様で落とさない**)

### テスト(test_solution.py)
- 最低4ケース。典型・境界・エラー系(仕様にあれば)がある
- パラメータ化された複数ケースで、例の値の丸暗記では通らない
- 引数を書き換えない・遅延評価・例外の型など、問題の「狙い」そのものを確かめている
- 時間やランダムに依存せず、何度実行しても同じ結果になる(sleep は短く、タイミングで判定しない)
- テスト名とコメントから、何を確かめているか分かる

### ヒント(hints)
- 3段階で、段階1 → 3 の順に具体的になる
- **どの段階にも、貼れば動くコードがない**(1行の断片まで)
- 段階3の手順どおりに書けば合格できる

### 模範解答(solution)・その他
- Pythonic で、学習者のお手本になる(型ヒント・内包表記・標準ライブラリ)
- 難易度がレベルに合う(L1 基礎 / L2 中級 / L3 標準ライブラリ / L4 実務)、5〜20分で解ける
- php_note は事実として正しく、PHPとの違いが学びになっている

## 報告フォーマット
```
| id | 判定 | 指摘 | 対応 |
|---|---|---|---|
| l1-005-mutable-default | ⚠️→✅ | `= []` のままでも合格できた(--try で実証) | デフォルト値 None を仕様とテストに追加 |
| l3-002-group-anagrams | ✅ | なし | - |
```
- 判定: ✅ 問題なし / ⚠️ 要修正(修正したら ⚠️→✅)/ ❌ 作り直しが必要
- `--try` で実証した抜け穴は「実証」と明記する。推測だけの指摘と区別する
- 修正はユーザーの指示がなければ提案にとどめる。ただし依頼が「レビューして直して」なら修正まで行う
