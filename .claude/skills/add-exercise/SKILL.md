# add-exercise

## 入力(ユーザーに確認する。不足していれば質問する)
- トピック(例: dict, generator, pathlib)
- レベル(1基礎 / 2中級 / 3標準ライブラリ / 4実務)
- 難易度の意図(何を身につけさせたいか。例:「`collections.Counter` を知らなくても書けるが、知っていると1行になる」)
- 形式(省略時は write + pytest)

## 手順
1. **重複確認**: `uv run python scripts/verify_solutions.py --list` で既存一覧を見る。
   同じ topic で狙いが同じ問題があれば、ユーザーに伝えて方向を変える。
2. **連番と配置を決める**: `exercises/level<N>/<NNN>_<slug>/`。NNN はそのレベル内の次の番号。
   id は `l<N>-<NNN>-<slug>`(slug は英小文字・数字・ハイフン)。
3. **テンプレートを複製**: このSkillの `templates/exercise.yaml` と(grading: pytest なら)
   `templates/test_solution.py` をコピーして書き換える。
4. **各項目を書く**(品質基準は下記)。
5. **実行検証(必須・省略禁止)**:
   `uv run python scripts/verify_solutions.py --id <id>`
   - 模範解答が全テスト合格、かつ初期コードが不合格であること
   - 失敗したら原因を直して再実行する。**テストを弱めて通さない**
6. **ハードコード耐性の確認**: テストの期待値を `if` で列挙しただけの「ずるい解答」を頭の中で
   想定し、それが通ってしまうならケースを追加する(パラメータ化した複数ケース・境界値)。
7. **全体の検証**: `uv run pytest tests/test_exercises.py` が通ることを確認。
8. **報告**: 追加した id・狙い・テストケースの観点を短く報告する。

## 品質基準
- **description**: 関数名・引数・戻り値・入力の前提(空や負数の扱い)を曖昧さなく書く。例を1つ以上
- **starter_code**: シグネチャ(型ヒント付き)だけ。そのままでは必ず不合格になること
- **tests**: 典型・境界(空、1要素、重複など)・エラー系(仕様にあれば)。最低4ケース。
  テスト名は何を確かめているか分かる名前に
- **hints**: 3段階で徐々に具体的に。**どの段階でも完成コードを書かない**
- **solution**: Pythonicで、学習者のお手本になる書き方(型ヒント・内包表記・標準ライブラリ)
- **php_note**: PHPとの違いが学びになる場合のみ書く(無理に書かない)
- **en**: title・description・hints・php_note(初期コードにコメントや docstring があれば starter_code も)の英訳(画面の English 表示用。全問必須で、
  tests/test_exercises.py が確認する)。php_note は日本語と英語の両方に書くか、両方省略する。
  テストが日本語の出力を確かめる問題では、英訳でもその文字列をそのまま示す。
  en.starter_code はコメント・docstring 以外を変えない(tests/test_exercises.py が確認する)
- 1問は 5〜20分で解ける粒度に
- time_limit_sec は既定(5秒)のままにする。重い処理が必要な問題は作らない

## よくある落とし穴
- **YAMLの記号**: hints を1行形式で書くと `: ` `{` `"` で壊れる。テンプレートどおり `- >-` で書く
- **ヒントと仕様の食い違い**: ヒントどおりに書いた解答がテストに落ちないか確認する
  (例: 「isupper で判定」とだけ書くと全角英字を弾くテストに落ちる)
- **lint**: test_solution.py も `ruff check` の対象。全角英字などは `\uXXXX` で書く
- **サンドボックス**: 環境変数は空・作業ディレクトリは一時ディレクトリ。ファイルを使う問題は
  `tmp_path`、環境変数を使う問題はテスト内で設定する。ネットワークは使わない(偽物を渡す)
